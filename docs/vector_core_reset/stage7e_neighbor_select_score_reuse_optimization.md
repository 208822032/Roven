## 5. Before complexity / behavior

Before:

```text
level0 full neighbor list
  -> find worst existing neighbor
  -> recompute distance(slot, existing_neighbor) for each scan entry
```

At 1K / 384-1024d this produced about 1.8M `neighbor_select_distance_recompute_count`, almost entirely from level0.

## 6. After design

Added manager-independent core-local derived state:

```text
kvs_hnsw_index_t.level0_neighbor_scores:
  one float per level0 neighbor slot
  score is relative to the owning level0 slot
```

Maintenance rules:

- Append / replace writes the score beside `level0_neighbors`.
- Remove shifts score entries with neighbor entries.
- Reset / reserve / clear-slot paths initialize or copy the score array.
- Existing-vector update refreshes level0 scores and invalidates worst cache.
- `kvs_hnsw_layer_find_worst_neighbor()` scans cached level0 scores when there are no deleted slots.
- Upper layers keep the old behavior.
- Custom `index->distance` keeps score recomputation where candidate score cannot be safely reused.

This preserves the same worst-neighbor comparison rule and changes only where level0 scores are read from.

## 7. Safety invariants

- `level0_neighbor_scores` is vector_core local derived state only.
- It is not persisted into RDB/AOF.
- It does not expose record_id, slot, or score cache internals in VSEARCH response.
- It does not access manager state, `g_vector_state`, `record_id_map`, scope, TTL, metadata, question, or answer.
- Score cache entries are updated on append / replace / remove / reset / reserve / existing-vector update.
- Level0 worst cache is still invalidated on graph mutation.
- Recall parameters are unchanged.

- `recall@10` did not regress.
