# Stage 50 Vector Core 重构后审计报告

- 审计日期：2026-06-26
- 审计范围：架构边界、正确性路径、benchmark 可信度、性能瓶颈归因、下一阶段路线
- 阶段性质：Audit-only
- 是否修改生产代码：否

## 1. 总结结论

KVLite vector_core 重构后的边界整体稳定：

1. `src/vector/core/flat` 和 `src/vector/core/hnsw` 没有访问 `g_vector_state`。
2. core 搜索结果仍然是 `record_id + score`。
3. manager 仍然负责 record store、scope/deleted 过滤、threshold、response 填充、RDB/AOF 后重建。
4. record store 仍然是 source of truth；flat / hnsw / faiss / hnswlib index 都是 derived state。
5. Stage 4B overfetch 修复后，benchmark 的 recall 结论可信；但当前 benchmark 还不能拆分 backend search、manager resolve、response assembly。
6. 下一轮第一优化阶段应选择 manager 共同瓶颈，而不是直接优化 core_hnsw memory/rebuild。

推荐下一阶段：

```text
Next Stage:
  Stage 5A: manager record_id fast resolve

Reason:
  1. 影响 core_flat、core_hnsw、faiss_flat、faiss_hnsw、hnswlib_hnsw 所有 backend。
  2. 当前 resolve 在 overfetch 后复杂度是 O(raw_topk * record_store_capacity)。
  3. 优化可以完全留在 manager 边界内，不改变 vector_core、RDB/AOF、backend ops 签名或 response 格式。
```

## 2. 核心问题回答

### Q1: core 是否仍然只处理 record_id / vector / score？

结论：是。新 core 实现保持在边界内。

证据：

- `include/vector/kvs_vector_core.h` 中 `kvs_vector_hit_t` 只有 `record_id` 和 `score`。
- `src/vector/core/flat/*` 只保存 vector、slot_to_record_id、deleted_flags、id-slot map 等 index-local state。
- `src/vector/core/hnsw/*` 只保存 vector、graph、slot_to_record_id、deleted_flags、id-slot map、visited tags、search context 等 index-local state。
- 静态检查显示 `src/vector/core` 没有 `g_vector_state` 代码命中。

说明：

- core 内部的 `deleted_flags` 是 index-local 逻辑删除标记，不是 manager 的业务 deleted/scope/TTL/metadata 过滤。

### Q2: manager 是否完全负责 scope / TTL / metadata / response？

结论：当前主路径基本是。

证据：

- `kvs_vector_manager_resolve_hits()` 负责 threshold、record_id 回表、ACTIVE/deleted 过滤、scope 过滤、`kvs_vector_search_result_t` 填充。
- core 不组装 response，也不处理 question/answer/scope。

注意：

- `kvs_vector_manager_resolve_hits()` 中有注释说明 TTL filtering 当前没有在该兼容路径中重复实现；TTL 仍然属于 manager 责任，不能下沉到 core。本阶段只记录风险，不实现修复。

### Q3: backend adapter 是否仍存在 manager 语义泄漏？

结论：存在，但限制在旧 adapter 边界内，没有污染 `src/vector/core`。

证据：

- `src/vector/kvs_vector_faiss_ops.c` 和 `src/vector/kvs_vector_hnswlib_ops.c` 仍实现旧 `kvs_vector_index_ops_t`，search 直接返回 `kvs_vector_search_result_t`。
- 两个 adapter 在 add 时调用 `kvs_vector_manager_get_active_record_id_by_index()`。
- 两个 adapter 在 search 后调用 `kvs_vector_manager_resolve_hits()`。
- `hnswlib_ops_search()` 读取 `g_vector_state.ann_index.ef_search`，属于 backend adapter 对 manager/global state 的依赖。

判断：

- 这是旧 adapter 兼容层债务，不是 vector_core 边界回退。
- 后续不要把这些 adapter 当作新 vector_core backend 的设计模板。

### Q4: overfetch 修复后，manager resolve 是否成为所有 backend 的共同瓶颈？

结论：是，至少是当前最明确的共同瓶颈。

证据：

- core_flat/core_hnsw/faiss/hnswlib 都使用 `topk * 4 + 32` overfetch。
- 所有 backend raw hits 最终都会进入 `kvs_vector_manager_resolve_hits()`。
- `kvs_vector_manager_resolve_hits()` 当前对每个 hit 扫描 `g_vector_state.store.capacity`。

复杂度：

```text
当前：O(raw_topk * record_store_capacity)
目标：O(raw_topk)，通过 manager-owned record_id -> slot/record fast path
```

### Q5: core_hnsw memory / rebuild 问题是否应该立刻处理？

结论：不应作为下一阶段第一目标。

它们是真问题，但应排在 P1/P2：

- Stage 4B 100K：core_hnsw memory 334,510,288 bytes，hnswlib 35,651,584 bytes，约 9.4x。
- Stage 4B 100K：core_hnsw rebuild 18,771.988 ms，hnswlib 39.633 ms。
- 代码证据：core_hnsw upper layer 邻接表按 `capacity * KVS_HNSW_MAX_LEVEL * M` 预分配，而 HNSW 高层天然稀疏。

暂缓原因：

- memory layout / rebuild 优化只影响 core_hnsw，不是共性瓶颈。
- 风险明显高于 manager resolve fast path。
- 当前 benchmark 还不能拆分 add-time search、neighbor selection、memset/reset、manager resolve 等内部耗时。

### Q6: benchmark 是否能准确拆分 backend search 与 manager resolve？

结论：不能。

当前可信：

- Stage 4B overfetch 修复后的 recall@10。
- 端到端 VSET / VSEARCH 延迟。
- rebuild wall time。
- RDB load+rebuild startup time。

当前不可信或不可拆：

- backend search time。
- manager resolve time。
- response assembly time。
- per-query raw candidate count 与过滤后数量。

判断：

- Stage 4B 的 recall 结论可信。
- Stage 4B 的 VSEARCH 端到端趋势有参考价值。
- 精确瓶颈归因仍需要 VSEARCH profiling。

### Q7: 下一步优化应该选低风险共性瓶颈，还是直接优化 core_hnsw？

结论：选择低风险共性瓶颈，即 Stage 5A manager record_id fast resolve。

原因：

- 影响所有 backend。
- 不跨越 manager/core 边界。
- 不改变持久化格式。
- 不改变 response 格式。
- 可用现有 regression 加一个 stale-id/slot-reuse 测试验证。

## 3. 架构边界审计

### 稳定边界

core 当前职责：

- record_id 到内部 slot 的映射。
- vector 存储和 index-local search state。
- 输出 `kvs_vector_hit_t`。
- index-local mark_delete。
- 不解析 question/answer/scope。
- 不访问 manager record store。
- 不组装 response。

manager 当前职责：

- record store。
- question/scope id map。
- VSET / VSEARCH / VDEL / VINDEX / VINFO 语义。
- AOF / RDB / load / replay / rebuild orchestration。
- threshold / scope / deleted / active filtering。
- response-visible 字段填充。

### 边界风险

风险 1：旧 internal header 仍职责混杂。

- `include/vector/kvs_vector_index_internal.h` 仍包含 `scope`、`threshold`、`record_index` 和直接输出 manager result 的旧接口。
- 这是迁移期债务，不是 Stage 50 新问题。

风险 2：faiss/hnswlib adapter 仍是旧 manager adapter。

- 它们不是干净的 `kvs_vector_core_ops_t` backend。
- 它们用于 benchmark / external backend 兼容，不应作为新 core 代码模板。

风险 3：manager resolve 缺少 record_id fast path。

- overfetch 修复提高 recall 后，raw hits 增多，resolve O(n) 成本被放大。

## 4. 正确性路径审计

### VSET 新增 / 更新同 key+scope

状态：已覆盖。

证据：

- core_flat / core_hnsw correctness tests 都覆盖了同 question/scope 更新 answer。
- 测试检查更新后新 answer 可见。
- 测试检查 VSEARCH 不出现重复 question。

风险：

- 当前测试默认更新不改变 embedding 语义。若未来支持更新 embedding，需要单独审计 backend update/rebuild 策略。

### VSEARCH topK / overfetch / threshold / scope filtering

状态：基本覆盖。

证据：

- Stage 4B 后 core_flat/core_hnsw/faiss/hnswlib 都有 `topk * 4 + 32` overfetch。
- regression 测试覆盖 scope 隔离。
- benchmark 使用 core_flat 作为 recall ground truth。

风险：

- benchmark 没有拆 threshold cost。
- benchmark 没有记录 raw_topk、resolve 前候选数、过滤后数量。

### VDEL / repeated delete

状态：已覆盖。

证据：

- core_flat/core_hnsw correctness tests 检查删除后搜索不可见。
- repeated delete 后 core deleted count 保持稳定。

风险：

- manager 会释放 slot 给后续记录复用；Stage 5A 若加入 fast resolve，必须验证 record_id 不会因为 slot 复用而误解析。

### VINDEX REBUILD

状态：已覆盖。

证据：

- core_flat/core_hnsw rebuild tests 删除记录后执行 rebuild。
- rebuild 后 deleted count 归零。
- scoped search 仍正确。

风险：

- core_hnsw rebuild 在 100K 下极慢，后续应单独 profiling。

### RDB load + rebuild

状态：core_flat/core_hnsw 已覆盖。

证据：

- RDB reload tests 验证 active records、update 保留、deleted 隐藏、reload 后显式 rebuild。
- Stage 4B benchmark 说明 core_hnsw 100K 在 wait_port timeout 足够时可以 pass。

风险：

- hnswlib_hnsw 100K RDB reload 仍失败，表现为 port not ready within 120s。应作为 P1 benchmark/backend attribution，不能直接当作 core 架构问题。

### AOF replay

状态：core_hnsw 已覆盖。

证据：

- AOF replay test 验证 active records、update、delete、search、rebuild after replay。

### stale record_id / slot reuse

状态：Stage 5A 必须重点覆盖。

当前安全性：

- record_id 单调递增，不复用。
- 当前 manager resolve 扫描 record_id，因此 slot 复用不会把旧 record_id 误解析为新 record。

Stage 5A 风险：

- fast path 必须验证 slot 内 record 的 id 仍等于请求的 record_id。
- fast path 必须验证 ACTIVE 且未 deleted。

### deleted / inactive / expired record

状态：

- inactive/deleted filtering 当前在 manager resolve 中存在。
- core 也有 index-local deleted slot 抑制。
- TTL 仍是 manager 责任，不应下沉到 core。

## 5. Benchmark 可信度审计

### 可信结论

Stage 4B 已修复主要 overfetch 公平性问题：

- hnswlib_hnsw recall@10：10K 为 0.9980，100K 为 0.9960。
- faiss_flat recall@10：10K 为 0.9990，100K 为 0.9950。
- core_flat 仍是可信 exact ground truth。

2026-06-26 当前 10K rerun：

| backend | status | VSEARCH avg ms | recall@10 | index memory bytes | rebuild wall ms | RDB load+rebuild ms |
|---|---:|---:|---:|---:|---:|---:|
| core_flat | pass | 0.549 | 1.0000 | 9,322,496 | 3.563 | 150.890 |
| core_hnsw | pass | 0.229 | 0.9870 | 41,826,512 | 1,221.799 | 2,610.124 |
| hnswlib_hnsw | pass | 0.573 | 0.9980 | 4,456,448 | 3.393 | 11,844.317 |
| faiss_flat | pass | 10.807 | 0.9990 | 0 | 3.187 | 150.932 |
| faiss_hnsw | pass | 0.279 | 0.9960 | 0 | 3.268 | 150.919 |

### benchmark 限制

1. `timed_cmd()` 测的是完整 RESP command round trip。
2. VSEARCH latency 包含 embedding path、backend search、manager resolve、response formatting、socket overhead。
3. 当前没有 backend / resolve / response 拆分。
4. FAISS `index_memory_bytes` 仍为 0，不能用于内存比较。
5. port selection 使用 bind(0)+close，有 TOCTOU 竞争风险。

### benchmark 使用结论

可以用于：

- recall 对比。
- 端到端 VSEARCH 趋势。
- rebuild wall time。
- RDB load+rebuild wall time。

不应直接用于：

- 精确 backend search latency 归因。
- 精确 manager resolve latency 归因。
- FAISS memory 对比。

## 6. 性能瓶颈归因

### Bottleneck A: manager resolve O(n)

优先级：P0

目标：

- 将 manager resolve 从每个 hit 扫描整个 record store，改为 manager-owned record_id fast path。

证据：

- `kvs_vector_manager_resolve_hits()` 对每个 hit 遍历 `store.capacity`。
- corrected overfetch 后 raw hit 数通常为 `topk * 4 + 32`。
- 所有 backend 都走这一 resolve 路径。

影响范围：

- core_flat / core_hnsw / faiss_flat / faiss_hnsw / hnswlib_hnsw。

风险等级：

- 低到中。

允许修改文件：

- `include/vector/kvs_vector_manager.h`
- `include/vector/kvs_vector_record.h`
- `src/vector/kvs_vector.c`
- `src/vector/kvs_vector_index.c`
- focused tests under `tests/`
- stage report under `docs/vector_core_reset/`

禁止修改内容：

- 不改 `src/vector/core/*`。
- 不改 RDB/AOF 格式。
- 不改 `kvs_vector_index_ops_t` 签名。
- 不改 response 格式。
- 不优化 core_hnsw memory/rebuild。

验收测试：

- 现有 core_flat/core_hnsw correctness/rebuild/RDB/AOF tests。
- 新增 stale-id/slot-reuse focused test。
- corrected benchmark compare pass。

benchmark 指标：

- 10K VSEARCH avg/p50/p95 before/after。
- recall@10 不回退。
- 可选 100K benchmark。

是否推荐立即执行：

- 是。

### Bottleneck B: VSEARCH profiling 缺口

优先级：P0

目标：

- 增加 backend search / manager resolve / response assembly 的 timing/count 拆分。

证据：

- 当前 benchmark 只能看到端到端 VSEARCH。
- FAISS latency 方差较大，不能只凭 endpoint timing 做精确归因。

影响范围：

- 所有 backend。
- 后续优化决策可信度。

风险等级：

- 低。

允许修改文件：

- `include/kvs_vector.h`
- `include/kvs_vcmd_profile.h`
- `src/core/kvs_vcmd_profile.c`
- `src/vector/kvs_vector.c`
- `scripts/bench_vector_core_compare.py`
- focused tests/docs。

禁止修改内容：

- 不改外部 response 格式，除非使用已有 profiling/VINFO 机制。
- 不改 backend algorithm。

验收测试：

- vector core regression set。
- profiling smoke test 显示 VSEARCH 后 backend/resolve timing 非零。

benchmark 指标：

- backend_search_us。
- resolve_us。
- result_format_us，如果实现成本可控。

是否推荐立即执行：

- 是，但不要和 core_hnsw 优化混在同一阶段。

### Bottleneck C: core_hnsw memory

优先级：P1/P2

目标：

- 降低 core_hnsw graph memory。

证据：

- 100K Stage 4B：core_hnsw memory 约为 hnswlib 的 9.4x。
- upper adjacency 当前按所有节点、所有可能 level 预分配。

影响范围：

- core_hnsw only。

风险等级：

- 中到高。

允许修改文件：

- 仅未来专门设计阶段允许 `src/vector/core/hnsw/*`。

禁止修改内容：

- 不应在 Stage 5A 处理。
- 不和 manager resolve 混合。

验收测试：

- full core_hnsw regression。
- recall benchmark。
- memory before/after。

benchmark 指标：

- memory_bytes 10K/100K。
- recall@10。
- VSET/rebuild/search latency。

是否推荐立即执行：

- 否。

### Bottleneck D: core_hnsw rebuild

优先级：P1

目标：

- 先 profiling，再分段优化 rebuild。

证据：

- 100K Stage 4B：core_hnsw rebuild 18.8s，hnswlib rebuild 39.6ms。

影响范围：

- core_hnsw rebuild / RDB load。

风险等级：

- 中。

允许修改文件：

- `src/vector/core/hnsw/*`
- core_hnsw-specific tests
- benchmark/profiling scripts

禁止修改内容：

- 不和 manager resolve 同阶段混做。
- 不改持久化格式。

验收测试：

- core_hnsw correctness/rebuild/RDB/AOF。
- recall benchmark 不回退。

benchmark 指标：

- 10K/100K rebuild wall ms。
- per-phase rebuild timing。

是否推荐立即执行：

- 否。

### Bottleneck E: hot-path malloc/free

优先级：P1

目标：

- 减少 search hot path 中 per-query allocation。

证据：

- core_flat/core_hnsw adapter 每次 VSEARCH 分配 `hits`。
- faiss/hnswlib adapter 每次 VSEARCH 分配 labels/scores/hits。
- core_flat search 内部也分配临时 heap array。

影响范围：

- 多个 backend 的 VSEARCH latency 和 p95 variance。

风险等级：

- 中。buffer reuse 必须线程安全。

允许修改文件：

- 对应 adapter/search 文件。
- focused tests/profiling。

禁止修改内容：

- 不改 response 格式。
- 不使用跨线程不安全 static buffer。

验收测试：

- correctness regressions。
- benchmark compare。

benchmark 指标：

- VSEARCH p95。
- malloc count，如果有 profiling。

是否推荐立即执行：

- 否，排在 manager resolve 之后。

## 7. P0 / P1 / P2 路线图

### P0: 共性低风险优化

1. manager resolve O(n) -> record_id fast path。
2. VSEARCH profiling 补齐 backend / resolve / response 拆分。
3. benchmark 统计口径标注 endpoint vs internal metrics。
4. VINFO 补齐 backend capacity / memory stats，尤其 FAISS memory_bytes。

### P1: 局部性能优化

1. core_hnsw rebuild 慢归因与分段优化。
2. core_hnsw memory layout 降低前的 profiling/design。
3. VSET resize/reserve 优化。
4. hnswlib RDB reload 100K fail 归因。
5. hot-path allocation reduction。

### P2: 结构性优化

1. core_hnsw graph memory layout 重构。
2. core_hnsw neighbor selection 优化。
3. index shard / partition。
4. scope-aware search。
5. graph persistence snapshot。
6. batch VSET / VSEARCH。
