# KVLite 阶段 3：异步写盘最小闭环

## 1. 本阶段目标

阶段 1 已完成统一日志出口，阶段 2 已把 `log_level` 和 `log_file` 接入配置。本阶段只做“异步写盘最小闭环”，不做滚动、采样、模块级动态控制，也不把日志系统工程化过度拆分。

目标是让业务线程不再直接承担文件 I/O，而是把日志记录交给一个有界队列，由后台线程统一 flush 到目标输出。

## 2. 当前日志链路分析

当前实现里，日志主链路是：

1. 业务代码通过 `KVS_LOG_*` 宏进入 [include/kvs_log.h](../../include/kvs_log.h)
2. [src/utils/kvs_log.c](../../src/utils/kvs_log.c) 负责统一格式化
3. 新增的 [src/utils/kvs_log_writer.c](../../src/utils/kvs_log_writer.c) 负责入队、后台 flush、以及必要时的同步退化
4. 初始化由 [src/core/kvstore.c](../../src/core/kvstore.c) 在配置加载完成后触发

阶段 2 之前，日志最终是直接写到 `stderr` 或文件流；阶段 3 之后，异步模式下文件 I/O 只在后台线程中执行。同步模式仍保留原有直写路径，兼容现有行为。

## 3. 异步方案设计

### 3.1 最小结构

我采用的是一个简单、稳定、可验证的有界环形队列，而不是无锁队列。

原因很直接：

- 日志入口是多线程的，不能沿用现有单生产者队列。
- 这一步的重点是正确性和最小侵入，不是压榨极限吞吐。
- 一个 `mutex + condvar + ring buffer` 的方案更容易验证退出和丢弃语义。

### 3.2 线程模型

- 前台线程：格式化单条日志记录，然后尝试入队。
- 后台线程：从队列批量取出记录，统一写入目标流并 flush。

### 3.3 队列实现

- 队列是有界的，当前实现使用固定容量 `256`。
- 每条记录预留固定长度缓冲区，避免额外堆分配。
- 队列满时不阻塞业务线程等待消费者。

### 3.4 默认行为

`log_async` 默认是 `no`。

原因：

- 最稳妥，和阶段 1 / 阶段 2 的同步行为完全兼容。
- 更容易验证，也更容易定位问题。
- 异步模式是显式开启的优化开关，而不是默认行为变化。

## 4. 队列满时的退化策略

队列满时，采用最小且明确的策略：

1. `INFO` / `DEBUG` 日志直接丢弃新来的记录。
2. `WARN` / `ERROR` 不丢弃，改为同步直写到当前输出流。
3. 丢弃次数累加统计，避免 silent failure。

这里对 `ERROR` 的处理选择了“同步退化而不是丢弃”。原因是错误日志通常比性能更重要，且这种退化只会在队列满这种异常压力下出现。

实现上，这意味着异步模式下大部分日志仍然走队列，但在高压场景里，高优先级日志会优先保留可见性。

## 6. 配置与生命周期

### 6.1 新增配置项

- `log_async = yes|no`

### 6.2 初始化流程

启动顺序保持为：

1. 读取默认配置
2. 解析配置文件
3. 再次应用命令行覆盖
4. 按最终配置初始化日志系统

当 `log_async = yes` 时，日志 writer 会在初始化阶段创建后台线程和队列。

### 6.3 退出流程

退出时：

1. 先停止接收新的日志事件
2. 再唤醒并等待后台线程退出
3. flush 队列中剩余记录
4. 回收线程、队列和文件句柄

这样可以保证进程不会因为日志线程卡住退出。

## 7. 验证步骤与结果

### 7.1 同步模式

使用 `log_async=no` 启动，日志仍按原逻辑正常输出，行为与阶段 2 保持一致。

### 7.2 异步模式

使用 `log_async=yes` 启动后，日志可以正常写入文件或 `stderr`，启动摘要中会显示实际模式为 `async`。

### 7.3 高压日志

通过高频协议错误场景制造大量日志，可以观察到业务线程不再被文件 I/O 直接拖住；队列满时会触发低优先级丢弃和高优先级同步退化。

### 7.4 队列打满

当队列被打满时，低优先级日志的丢弃计数会累加，并在退出阶段输出汇总信息，避免静默丢失。

### 7.5 退出落盘

退出时后台线程会先把剩余队列刷完，再关闭流，因此剩余日志会尽量落盘。

## 8. 当前遗留问题

- 这里只做了最小闭环，没有实现滚动、采样、限流或远程采集。
- 队列容量是固定常量，没有做配置化。
- 仍然没有把所有 legacy 输出点全部迁移到更细粒度的日志语义上。

## 9. 下一步建议

1. 继续逐步迁移剩余 legacy `printf` / `fprintf` 输出，但不要扩大本阶段的设计边界。
2. 如果后续确实需要更高吞吐，再考虑把队列容量、批量 flush 和 drop 策略做成更完整的运行时参数。
