# Route C Re-entry Stage 1 Regression Investigation

Date: 2026-07-20

## 1. Scope and conclusion

This investigation was read-only-first. No production or test behavior was
changed. Temporary TTL diagnostics were removed, the normal release build was
restored, and the two root-level snapshot files generated by the vector test
were removed.

Conclusions:

- The reported immediate `TTL=-2` was not reproduced. The current TTL
  calculation and owner-assertion-enabled runtime both behave correctly. A
  one-second deadline being consumed by separate client process startup or
  scheduling remains the high-probability explanation, but is not a confirmed
  root cause.
- The normalization failure was reproduced and its root cause is confirmed:
  the test's direct embedding fixtures have `norm_sq=0.3125` while the test
  enables normalized-vector validation. The bytes and dimension remain intact
  from fixture through prepare and commit. The failing path does not perform
  persistence.
- Neither issue blocks Replication Stage 1A. Fix the vector test fixture before
  treating the product-integration suite as green. Make the TTL test harness
  and timing check robust in a separate test-only change.

No pre-Stage-1 binary was executed. Source comparison strongly argues that the
owner-contract changes did not cause either observation, but regression
attribution remains `unknown` rather than being stated as proven.

## 3. TTL investigation

### 3.1 Minimal reproduction

A single persistent RESP connection ran the following sequence for all four
storage backends, once with background scan enabled and once disabled:

```text
SET/RSET/HSET/SSET key value
EXPIRE key 1
TTL key
GET/RGET/HGET/SGET key
sleep 1.05 seconds
TTL key
GET/RGET/HGET/SGET key
```

Immediate `TTL` was `0` or `1`, and the value was readable. After 1.05 seconds,
`TTL` was `-2` and the value was absent. Scan enabled/disabled behavior was the
same, proving lazy expiration does not depend on the scanner.

Temporary internal diagnostics observed, for each backend:

```text
EXPIRE now_ms       = 1784534603895
expire_at_ms        = 1784534604895
assigned delta_ms   = 1000
immediate TTL now_ms= 1784534603895
delayed TTL now_ms  = 1784534604946
```

### 3.2 Call-chain evidence

- `kv_now_ms()` uses `CLOCK_REALTIME` and returns milliseconds:
  `include/kvs_types.h:78`.
- `EXPIRE` parses seconds, multiplies by 1000, and stores
  `now_ms + delta_ms`: `src/core/kvs_operation.c:507`.
- `TTL` returns `-2` only when the absolute deadline has passed and otherwise
  floors remaining milliseconds to seconds: `include/kvs_types.h:88` and
  `src/core/kvs_operation.c:549`.
- `TTL` and reads perform lazy expiration before returning; background scan is
  not required: `src/core/kvs_operation.c:467` and
  `src/core/kvs_operation.c:495`.
- `git diff HEAD` shows that Stage 1 only added the owner assertion to
  `ttl_expire_observed_key()`. `git show HEAD:src/core/kvs_operation.c` has the
  same time conversion and command flow.

An assertions-enabled build plus the full four-backend TTL MVP passed. The
array TCP TTL replication regression also passed with assertions enabled,
covering replicated `EXPIRE`, lazy delete, `PERSIST`, overwrite, delete, and
full sync. No owner fail-fast occurred.

### 3.3 Classification and recommendation

Confirmed facts:

- The current code assigns exactly 1000 ms for `EXPIRE 1`.
- Immediate `TTL=-2` is not reproducible in the focused or full business run.
- All four storage backends agree.
- Stage 1 assertions do not change the successful TTL apply/retry path.

High-probability, not confirmed: the original test invokes a new client process
for each command. Under load, the one-second interval between `EXPIRE` and
`TTL` can expire before the check.

Minimum fix: update the test harness to create its data directory or disable
unused vector snapshot initialization, use the built client path, and make the
immediate check timing-safe (for example `EXPIRE 2` or a measured deadline).
Do not change production TTL units or lazy-expire semantics.

## 4. Normalization investigation

### 4.1 Confirmed root cause

The fixture at
`tests/vector_core_hnsw_v2_product_integration_test.c:316` defines:

```c
const float vec_a[64] = {0.25f, 0.5f, 0.0f, 0.0f};
const float vec_b[64] = {0.0f, 0.5f, 0.25f, 0.0f};
```

Each vector has `norm_sq = 0.25^2 + 0.5^2 = 0.3125`. `git blame` assigns the
fixture to commit `07fdc6c`; it predates the current owner-contract diff.

The diagnostic recorded the same dimension, byte count, norm and checksum at
all available stages:

```text
fixture_a:             dim=64 bytes=256 norm_sq=0.312500000 checksum=2756131f2c00ceb0
prepared_before_commit:dim=64 bytes=256 norm_sq=0.312500000 checksum=2756131f2c00ceb0
record_a_after_commit: dim=64 bytes=256 norm_sq=0.312500000 checksum=2756131f2c00ceb0
```

Vector B likewise retained checksum `5a1bef74008f8d10`. There is no wrong
dimension, omitted float, truncation, or partial recovery. Despite its name,
`expect_rebuild_after_load_like_path()` commits in-memory prepared vectors and
calls rebuild directly; it does not write or read RDB/AOF/snapshot data.

`kvs_vector_set_prepare_with_embedding()` copies exactly
`embedding_dim * sizeof(float)` without normalization
(`src/vector/kvs_vector.c:3404`). Commit transfers that allocation unchanged
(`src/vector/kvs_vector.c:3671`). Recovery contract validation correctly
rejects a non-unit vector when normalization is enabled
(`src/vector/kvs_vector.c:3220`). RDB independently writes and reads the same
dimension-derived byte count (`src/persistence/kvs_rdb.c:173` and `:285`).

A `/tmp` control changed only the fixture values to `{0.6f, 0.8f}`. It produced
`norm_sq=1.000000048`, retained identical fixture/prepared/record checksums, and
the complete product-integration binary passed.

### 4.2 Stage 1 relationship and recommendation

`git diff HEAD` shows that Stage 1 additions in `src/vector/kvs_vector.c` are
owner assertions at commit, ID allocation, active-index mutation and rebuild
delta boundaries. Neither the fixture, byte copy nor recovered-record contract
changed. Those assertions do not mutate embeddings.

Minimum fix: change this test's direct embeddings to normalized vectors, such
as `{0.6f, 0.8f}`. Keep production recovery validation strict. Recovery must
reject invalid source-of-truth bytes rather than silently renormalize them.
