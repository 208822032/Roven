# KVLite 项目复盘文章生产准则

本文用于约束 `docs/interview-prep/` 下后续项目复盘文章的审计、选题、写作和验证流程。

目标是：

```text
严格尊重 Git 真实历史
以完整工程问题组织文章
避免按提交或 Stage 过度拆分
保留失败、返工和证据边界
提供可点击的源码与结果链接
为未来重大迭代保留成篇空间
```

---

## 一、基本执行边界

每次生成复盘文章前，必须：

1. 读取并遵守项目根目录 `AGENTS.md`。
2. 完整读取本文。
3. 读取已有 `docs/interview-prep/` 文章，确认上一章结束位置和写作风格。
4. 审计目标范围的 Git 提交、实际 diff、历史源码、阶段文档、测试和结果。
5. 每次只新增或修改一篇复盘文章。
6. 不修改生产代码、测试、配置、Makefile、结果文件和原始阶段文档。
7. 不执行：

```bash
git reset
git checkout
git stash
git clean
git commit
```

8. 不处理 worktree 中与本次复盘无关的已有修改。
9. 如果目标章节已经存在，必须原地审计和修订，禁止创建重复章节。
10. 完成当前文章后立即停止，不顺带生成下一篇。

---

## 二、文章划分原则

文章以“完整工程问题闭环”为单位，不以提交数量或 Stage 编号为单位。

一篇文章通常应包含：

```text
上一阶段遗留问题
→ 第一版方案
→ 问题暴露
→ 连续迭代和返工
→ 阶段性最终设计
→ 测试与结果
→ 当前缺陷
```

以下内容通常应合并为一篇：

* 解决同一个核心问题；
* 修改同一条主要调用链或数据结构；
* 前一阶段只是后一阶段的中间态；
* 单独拆开后无法形成完整工程故事；
* 面试时通常会一起讲述；
* 拆开后会重复大量背景和源码。

以下情况才适合拆成两篇：

* 核心工程问题发生变化；
* 数据结构、所有权模型或故障模型发生根本变化；
* 前一阶段已形成独立的测试和结果闭环；
* 两部分在面试中属于不同深挖主题；
* 合并后出现两条互不依赖的主线。

禁止：

```text
一个提交一篇
一个小优化一篇
一个测试修复一篇
一个 Stage 一篇
一个统计字段一篇
```

Stage 编号只能作为文章内部的时间节点，不能直接决定文章数量。

## 三、Git 历史审计要求

不得只看 commit message。

至少检查：

```bash
git status --short
git log --reverse --topo-order --date=short --format='%h %ad %s'
git show --stat <commit>
git show --format=fuller <commit>
git show <commit> -- <相关路径>
git diff <start>^..<end> --stat
git diff <start>^..<end> -- <相关路径>
```

需要查看历史源码时使用：

```bash
git show <commit>:<path>
git show <commit>^:<path>
```

每项能力必须区分：

```text
该提交当时已经实现
该提交只是中间态或骨架
后续提交才补齐
当前仍未完成
```

禁止用当前 HEAD 的最终实现描述早期阶段。

对于聚合提交，必须按文件路径、阶段文档和实际实现拆分主题，不能把整个提交中的所有代码都归入当前文章。

---

## 四、文档与实现的证据关系

阶段 Prompt、设计文档和路线规划只能说明“当时准备做什么”，不能直接证明已经实现。

事实优先级建议为：

```text
实际源码和 diff
> 测试与原始结果
> 实现或 closeout 报告
> 设计文档
> Prompt 和计划
> commit message
```

文章中的结论统一使用以下等级：

### 已经证明

有明确源码、测试和结果支撑。

### 基本证明

代码已接入实际路径，并有阶段测试或报告支持，但覆盖范围有限。

### 暂时观察到

仅在特定数据、规模、配置或阶段报告中出现。

### 尚未证明

缺少实现、规模验证、故障测试、真实数据或长期运行证据。

禁止：

* 把测试脚本存在写成测试已经通过；
* 把 benchmark 工具存在写成已有性能结果；
* 把 smoke test 写成规模结论；
* 把 1K 结果外推到 10K/100K；
* 把 synthetic vector recall 写成真实语义质量；
* 把 ANN exact recall 写成语义 qrels；
* 把 serialized size 写成 runtime memory；
* 把设计写成已完成实现；
* 使用找不到来源的性能数字。

## 五、文章内容要求

每篇文章应根据实际主题覆盖以下内容，不要求机械套用固定模板。

### 1. 上一阶段遗留问题

说明上一阶段已经完成什么、为什么仍不足以继续演进。

### 2. Git 范围与真实演进主线

明确：

```text
起始 commit
结束 commit
inclusive Git 范围
关键提交
中间态提交
不属于本章的修改
```

### 3. 核心源码导航

提供 8～12 个最关键入口，包括：

* 阶段起点历史源码；
* 核心结构体；
* 主调用链；
* 关键测试；
* 结果或阶段报告。

导航用于快速回看，不能替代正文解释。

### 4. 核心数据结构和调用链

必须讲清：

```text
谁拥有数据
谁可以修改状态
输入和输出 contract
主要调用链
生命周期
错误和失败路径
关键不变量
```

### 5. 中间态、失败和返工

必须保留：

* 初版不完整能力；
* 测试暴露的问题；
* 无效 benchmark；
* 参数未生效；
* 召回回退；
* 低收益优化；
* 被拒绝或回退的实现；
* 最终为什么止损或换路线。

不得把项目写成一次性成功。

### 6. 工程取舍

至少回答：

```text
为什么采用当前方案
考虑过哪些替代方案
为什么没有选择其他方案
当前方案牺牲了什么
什么条件下需要重新设计
```

### 7. 测试和结果

严格区分：

```text
correctness
smoke
stress
TSAN
index-only
endpoint/e2e
recall
语义 qrels
build
search
memory
cold start
```

每个结果都要说明“证明了什么”和“没有证明什么”。

### 8. 当前缺陷

主动记录：

* 尚未完成的能力；
* 设计债务；
* 性能瓶颈；
* 故障模型缺口；
* 测试盲区；
* 规模风险；
* 下一阶段触发条件。

### 9. Agent 辅助边界

诚实区分：

```text
我提出的问题
我设定的边界
我做出的设计和验收决策
Agent 辅助的代码、测试或文档工作
我发现和纠正的问题
我现在能独立解释和维护的内容
```

不得根据代码风格猜测逐行作者。

只有 Git 明确存在 `Co-Authored-By` 时，才能陈述对应协作事实。

### 10. 面试表达

至少包含：

* 1 分钟版本；
* 3～5 分钟版本；
* 常见追问；
* 回答要点；
* 容易夸大的内容。

面试表达必须能回答：

```text
为什么这样设计
不这样做会怎样
失败时如何处理
替代方案是什么
当前实现的边界是什么
```

## 六、源码、测试和结果链接规范

所有源码、头文件、测试、结果和阶段文档首次引用时，必须使用可点击 Markdown 链接。

### 当前 HEAD 文件

使用相对于 `docs/interview-prep/` 的仓库内链接：

```markdown
[`kvs_command_executor.c`](../../src/core/kvs_command_executor.c)
[`core_flat`](../../src/vector/core/flat/)
[`某阶段报告`](../vector_core_reset/example_report.md)
```

### 历史源码

先检查：

```bash
git remote get-url origin
```

如果仓库存在可用 GitLab/GitHub 浏览器地址，使用 commit-pinned 链接：

```markdown
[`2f1fc7f` 时的 `kvs_hnsw_v2_index_t`](仓库地址/-/blob/2f1fc7f/path#Lx-Ly)
```

行号必须通过实际历史文件确认：

```bash
git show <commit>:<path> | nl -ba
```

禁止猜行号。

如果没有可用浏览器地址，使用：

```text
<commit>:<path>
```

并给出查看命令：

```bash
git show <commit>:<path>
```

不得构造伪链接。

### 测试与结果

测试通过结论应同时引用：

```text
测试源码或脚本
+
原始结果或明确记录执行结果的阶段报告
```

如果只有测试文件，只能写“存在该测试”，不能写“测试通过”。

所有 recall、延迟、构建时间、内存、命中率等数字必须链接原始结果或明确阶段报告。

### 链接验证

完成文章后，必须检查所有本地相对链接。

要求：

```text
本地相对链接失效数 = 0
```

历史链接至少验证：

```bash
git cat-file -e <commit>:<path>
```

## 七、已有历史和未来章节的边界

当前文章只写已经发生并形成证据闭环的 Git 历史。

对于未来主题，只允许写：

```text
当前为什么未解决
进入下一阶段的触发条件
```

禁止提前展开未来完整设计、状态机、数据格式或结果。

不得使用以下终局式表述，除非项目确实已经结束：

```text
最终实现
全面完成
生产级完成
全部收口
最终架构
```

应使用阶段性表达：

```text
本阶段完成
阶段性可用
达到当前验证下限
形成工程闭环
仍保留后续演进空间
```

未来章节是否成篇，必须满足：

```text
实际代码落地
形成完整调用链
存在测试或结果
出现独立工程问题和取舍
```

只有设计、接口骨架或局部实验时，不应提前占用一篇文章。

---

## 八、文件数量与路线控制

当前已经发生的历史应压缩为有限的宏观文章。

不得为了减少篇数，把以下完全不同的主题强行合并：

```text
ANN 算法
文件格式和冷启动
在线 rebuild 并发发布
真实数据 benchmark
复制状态机
```

也不得为了增加篇数，把以下同一主线机械拆开：

```text
构图
搜索
recall
参数归因
局部优化
产品薄接入
```

每完成一章后，只规划下一篇标题和候选 commit 范围，不创建下一篇文件。

---

## 九、写后验证

完成文章后必须执行：

```bash
git status --short
git diff -- <目标文章>
```

新文件未跟踪时使用：

```bash
git diff --no-index /dev/null <目标文章>
```

检查：

```text
是否只新增或修改一篇文章
是否创建重复章节
是否修改生产代码
是否保持 Git 时间顺序
是否把聚合提交错误整体归类
是否重复上一章
是否提前消费下一章
是否把骨架写成完成能力
是否存在无来源数字
是否保留失败和低收益尝试
是否所有关键源码可点击
是否所有数字有证据
是否所有本地链接有效
```

## 十、每次任务的最终报告

最终只需要报告：

### 1. 章节审计

```text
目标文件
现有文件完整性等级 A/B/C/D
上一章和下一章边界
```

### 2. Git 范围

```text
起始 commit
结束 commit
inclusive range
关键提交
聚合提交如何处理
```

### 3. 文档覆盖

列出主要阶段组、commit 和文章小节。

### 4. 修改结果

```text
文件路径
最终标题
新增还是修订
是否只修改一篇
```

### 5. 链接结果

```text
当前源码链接数
历史链接数
测试链接数
结果/报告链接数
失效链接数
```

### 6. 核心结论

```text
原始问题
关键转折
阶段性设计
失败和低收益尝试
测试证明内容
尚未证明内容
当前缺陷
面试价值
```

### 7. 验证结果

```text
git status
diff 范围
是否修改生产代码
是否存在无来源数字
是否保持 Git 顺序
是否提前消费后续章节
本地链接失效数
```

### 8. 下一篇建议

只输出下一篇标题和候选 commit 范围，不生成正文。

## 十一、执行前自检

开始写入前先确认：

```text
我是否已经读取 AGENTS.md？
我是否已经读取本文？
我是否已经完整读取目标文章和上一章？
我是否已经查看实际 Git diff？
我是否已经读取历史源码？
我是否区分了设计和实现？
我是否确认目标章节是否已存在？
我是否明确了下一章边界？
```

任何一项无法确认时，先继续只读审计，不要直接写文章。
