## 一、项目定位分析

### 1.1 项目类型判定：Redis-like 内存 KV，非 RocksDB-like LSM KV

| 维度 | KvLite | Redis | RocksDB |
|------|--------|-------|---------|
| 存储介质 | 纯内存 | 内存 + 可选磁盘 | 磁盘优先（LSM-Tree） |
| 数据结构 | array/rbtree/hash/skiptable | SDS/ziplist/dict/skiplist | MemTable + SST |
| 持久化方式 | AOF + RDB（类 Redis） | AOF + RDB | WAL + Compaction |
| 协议 | RESP | RESP | 无（库接口） |
| 网络模型 | epoll/io_uring/协程 | epoll（单线程） | N/A |

**结论：KvLite 的设计参考系是 Redis，不是 RocksDB。面试和博客中应明确这一点，避免面试官用 LSM-Tree 的视角审视你。**

### 1.2 适合投递的岗位

| 岗位方向 | 匹配度 | 理由 |
|----------|--------|------|
| C/C++ 后端开发 | ★★★★★ | 核心语言、网络编程、系统编程 |
| 存储系统开发 | ★★★★☆ | KV 引擎、持久化、复制 |
| 基础架构/中间件 | ★★★★☆ | RESP 协议、多网络模型 |
| 高性能服务端 | ★★★★☆ | epoll/io_uring、Pipeline、benchmark |
| AI 基础设施 | ★★★☆☆ | 向量检索模块（加分项但非核心） |
| 数据库内核开发 | ★★★☆☆ | 缺少事务、WAL、MVCC 等关键特性 |

### 1.3 不适合的包装方向（风险警告）

| 错误包装 | 风险 |
|----------|------|
| "分布式 KV 数据库" | 没有分片、共识协议、故障转移，会被追问到崩溃 |
| "高性能替代 Redis" | 单线程执行模型、无 cluster 模式，skiptable 写性能低于 Redis |
| "向量数据库" | hash embedding 非语义模型，HNSW 为自实现，不宜对标 Milvus |
| "生产级存储系统" | 无灰度、无监控、无在线升级、无多版本兼容 |

**推荐定位：**
> "一个从零迭代的类 Redis 内存 KV 存储系统，涵盖 RESP 协议、多数据结构引擎、AOF/RDB 持久化、主从复制、多网络模型，并扩展了内置向量语义检索能力。定位为个人系统工程能力的综合训练项目，而非生产数据库产品。"

### 1.4 与成熟系统的差异化表述

**vs Redis：**
- 相同：RESP 协议、AOF/RDB、主从复制、TTL 语义
- 不同：多网络模型可切换（reactor/proactor/协程）、eBPF 辅助同步、内置向量检索
- 不如：无 cluster、无 sentinel、无 Lua 脚本、无 Stream 等高级数据结构

**vs RocksDB：**
- 完全不同：KvLite 是网络服务，RocksDB 是嵌入式库
- 相似点：跳表数据结构
- 正确表述："KvLite 在存储引擎层面与 RocksDB 不具备可比性，它是一个网络可访问的 KV 服务，更接近 Redis"

**vs Milvus/Faiss：**
- 相似点：HNSW 索引、FLAT/IVF 索引抽象
- 不同：embedding 使用本地 hash（非语义模型）、集成在 KV 引擎内部、不支持 GPU
- 正确表述："向量模块的索引框架借鉴了 Faiss 的设计，但定位是轻量级 AI Chat 会话缓存，非通用向量数据库"

### 1.5 各模块的能力体现

**最能体现 C/C++ 服务端能力的模块：**
1. Reactor 网络层（epoll + ET 模式 + 用户态缓冲区）
2. RESP 协议解析器（状态机 + Pipeline 批量处理）
3. 内存池（pool/system/jemalloc 三后端可切换）
4. io_uring Proactor 实现
5. tx_batcher（eBPF 路径的批量发送优化）

**最能体现存储系统能力的模块：**
1. AOF 追加写 + rewrite 压缩
2. RDB 快照保存与加载
3. TTL 惰性删除 + 后台扫描 + 全链路保持
4. 主从全量同步 + 增量复制
5. 四种数据结构的统一命令框架

**容易被追问的"炫技"模块：**
1. eBPF 辅助同步 — 需要清楚解释为什么不用 TCP 而要上 eBPF
2. io_uring Proactor — 需要解释实际收益和适用场景
3. ucontext 协程 — 需要解释为什么不用有栈协程/无栈协程
4. HNSW 自实现 — 需要解释和 hnswlib/faiss 的差异

## 二、项目演进路线

基于 git log 分析，我重构了 KvLite 的真实演进线：

### 阶段 1：基础 KV 存储引擎（2025-04 初）
- **目标：** 跑通一个能 SET/GET/DEL 的最小可用 KV
- **问题：** 从零搭建 C 项目基础设施
- **方案：** 
  - 最简单的 array 结构存储 key-value
  - TCP socket + 自定义文本协议
  - 单线程 accept + 处理
- **产出：** 基础 array SET/GET/DEL
- **结果：** 能用但性能差（线性扫描）
- **面试价值：** ★★☆☆☆ — 过于简单，但可以讲"为什么选择 C 语言"的设计决策

### 阶段 2：RESP 协议解析 + 多数据结构（2025-04 中）
- **目标：** 兼容 Redis 客户端生态，支持多种索引结构
- **问题：** 
  - 自定义协议无法用 redis-benchmark 压测
  - array 线性扫描在数据量大时性能差
- **方案：**
  - 实现 RESP 协议解析器
  - 引入 rbtree/hash/skiptable 三种索引结构
  - 统一命令框架（SET → KVS_CMD_SET, RSET → KVS_CMD_RSET...）
  - 命令表驱动分发
- **产出：** 四种数据结构 + RESP 协议 + 统一命令分发
- **结果：** 可以用 redis-benchmark 直接压测
- **面试价值：** ★★★★☆ — RESP 协议解析、命令表设计、多态存储

### 阶段 3：Pipeline 支持 + 性能优化第一轮（2025-04 末）
- **目标：** 提升单连接吞吐，追上 Redis baseline
- **问题：** 
  - 单命令单次 read/write 系统调用开销大
  - rbtree/skiptable 查找路径有重复遍历
  - array 线性扫描在大数据量下性能退化严重
- **方案：**
  - 用户态收发缓冲区（net_session + netbuf）
  - net_session_process_resp 批量解析 + 批量执行
  - 优化 rbtree/skiptable 热点查找路径
  - array 引入二分查找
- **产出：** Pipeline 批量处理 + 多轮性能优化
- **结果：** 四种数据结构读写 QPS 基本与 Redis 持平（commit: 37d2e7a）
- **面试价值：** ★★★★★ — Pipeline 设计、批量处理、性能剖析

### 阶段 4：TTL 过期管理（2025-05）
- **目标：** 实现完整的过期键管理
- **问题：**
  - 需要惰性删除 + 后台扫描兜底
  - TTL 需要在 RDB/AOF/主从同步中保持语义
  - 覆盖写需要自动清除旧 TTL
- **方案：**
  - `kv_now_ms()` + `kv_is_expired()` 工具函数
  - GET/EXIST/RANGE/SORT/FULLDUMP 路径惰性过滤
  - 后台扫描线程定期批量清理
  - AOF rewrite 跳过过期 key
  - 主从同步以 master TTL 为准
- **产出：** 完整的 TTL 链路
- **结果：** 全链路测试通过（test_ttl_all_backends.sh）
- **面试价值：** ★★★★★ — 惰性删除 vs 主动删除、一致性语义

### 阶段 5：AOF/RDB 持久化（2025-05 中）
- **目标：** 数据不因重启丢失
- **问题：**
  - AOF 三种 fsync 策略实现
  - AOF rewrite 如何不阻塞正常写入
  - RDB 快照的一致性问题
- **方案：**
  - AOF 追加写（no/everysec/always）
  - AOF rewrite：创建子 AOF，遍历内存数据重写
  - RDB save：遍历四种数据结构 + 向量数据序列化
  - 重启恢复：先加载 RDB，再重放 AOF
- **产出：** AOF + RDB 完整实现
- **结果：** 通过 10 万条数据恢复测试
- **面试价值：** ★★★★★ — 持久化策略、一致性、恢复流程

### 阶段 6：主从复制（TCP + eBPF）（2025-05 末至 2025-06）
- **目标：** 实现数据冗余和读写分离
- **问题：**
  - 全量同步如何进行
  - 增量复制如何保证顺序
  - eBPF 路径如何捕获流量
- **方案：**
  - TCP 路径：全量同步（RDB dump → slave） + 增量复制（实时转发写命令）
  - eBPF 路径：kprobe/tcp_sendmsg 抓取 master 出向流量 → ringbuf → ebpf_syncd → slave
  - tx_batcher 批量发送优化 eBPF 路径吞吐
- **产出：** TCP 主从 + eBPF 主从
- **结果：** TCP 模式对写吞吐影响 <5%，eBPF 批处理可提升约 30% vs 无批处理
- **面试价值：** ★★★★★（TCP）/ ★★★★☆（eBPF）— eBPF 需要谨慎表述

### 阶段 7：向量语义检索（2025-10 至 2026-05）
- **目标：** 扩展 AI Chat 语义缓存能力
- **问题：**
  - 需要 embedding 能力（远程 gRPC → 本地 hash）
  - 需要 ANN 索引提升搜索性能
  - 向量数据需要持久化
- **方案：**
  - V 族命令（VSET/VGET/VSEARCH/VDEL/VINFO/VINDEX REBUILD）
  - FAISS-like 索引抽象层（flat/HNSW/SQ8 Flat）
  - 本地 hash embedding（64 维确定性向量）
  - AVX2 距离计算后端
  - RDB 持久化向量记录 + 重启后 VINDEX REBUILD
- **产出：** 完整的向量语义缓存模块
- **结果：** 100K 向量 HNSW 搜索 p99 < 3ms（latency 模式）
- **面试价值：** ★★★★☆ — 索引设计、ANN 原理、embedding 取舍

### 阶段 8：多轮 benchmark + 性能调优（贯穿全程）
- **目标：** 验证性能、发现瓶颈、对标 Redis
- **问题：**
  - 需要与 Redis 同口径对比
  - 需要定位性能热点
  - 需要证明优化有效
- **方案：**
  - redis-benchmark 同参数压测
  - perf 火焰图定位热点
  - strace 对比系统调用次数
  - gdb 排查崩溃
  - ASan 检测内存问题
- **产出：** benchmark 体系 + perf 分析报告
- **结果：** `results/raw.csv` + `docs/benchmark_optimization_progress.md`
- **面试价值：** ★★★★★ — 工程素养、性能分析方法论

### 演进线总结（面试30秒版）

> "KvLite 从最基本的 SET/GET 开始，先实现了 RESP 协议兼容 Redis 生态，然后引入四种数据结构解决线性扫描性能问题。Pipeline 批量处理让吞吐追上了 Redis。接着做了 TTL 过期管理、AOF/RDB 持久化让数据不丢。然后做了 TCP 和 eBPF 两条主从复制链路。最近一年把向量语义检索加进来，做了 HNSW ANN 索引和 AVX2 距离计算优化。整个项目跨度一年半，每个模块都是先用起来、再压测定位瓶颈、再针对性优化。"

## 四、每篇博客详细大纲

### 第 1 篇：《从零迭代一个类 Redis KV：KvLite 的设计目标与演进》

#### 1. 背景：为什么做这个项目
- 研一学完操作系统和网络编程后，想找一个系统项目练手
- Redis 是一个"恰好大小"的参考对象：代码量适中、架构清晰、工业验证充分
- 目标不是替代 Redis，而是理解"一个网络 KV 服务是怎么建起来的"

#### 2. 问题：如果只是"写一个 KV 存储"就可以了吗
- 不是。一个可演示的 KV 和一个工程化的 KV 差距巨大
- 工程化意味着：协议兼容、数据可靠、性能可度量、边界可解释
- 所以需要一条演进路线

#### 3. 设计目标
- 网络可访问（非嵌入式库）
- 兼容 Redis 客户端（RESP 协议）
- 多种数据结构可切换
- 数据可持久化
- 支持基本复制
- 性能可与 Redis 对比
- 最终扩展向量检索能力

#### 5. 演进路线（时间线图 + 关键 commit 引用）
- 阶段 1~8 的简要说明（不要在总览里展开太细）

#### 6. 核心设计决策（为什么这样做）
- 为什么用 C：控制内存布局、系统调用直接、理解底层
- 为什么用 RESP：兼容 redis-cli 和 redis-benchmark
- 为什么单线程执行命令：简化并发控制，后续可扩展多线程
- 为什么不支持过期淘汰（eviction）：内存 KV 不如 Redis 有 maxmemory 需求复杂
- 为什么 hash embedding 而非调用模型 API：保持本地可复现、无外部依赖

#### 7. 验证方法

#### 4. Pipeline 批量处理设计
- 为什么需要 Pipeline：减少系统调用、减少网络往返
- 用户态缓冲区的设计：`netbuf_t` + `net_session_t`

### 第 4 篇：《AOF/RDB 持久化：从设计到验证》

#### 1. 背景
- KV 是内存数据库，重启数据就没了
- 需要两种持久化方式互相补充

#### 2. 问题：AOF vs RDB 的取舍
- AOF：数据安全（最少丢 1 秒），但文件大、恢复慢
- RDB：文件小、恢复快，但可能丢更多数据
- Redis 的做法：两者结合

#### 3. AOF 设计
- 三种 fsync 策略的实现
- AOF rewrite：`kvs_aof_rewrite.c`（1053 行）
- 为什么 rewrite 期间不能阻塞正常写入
- TTL 在 AOF 中的处理（过期 key 不写入、PEXPIREAT 转换）

#### 4. RDB 设计
- 序列化格式：四种数据结构 + 向量数据
- 快照一致性的处理（单线程天然无并发问题）
- 加载流程

#### 5. 重启恢复流程
- RDB 先加载 → AOF 重放 → 向量索引重建
- 为什么顺序不能乱

#### 6. 验证
- 10 万数据写入 → 重启 → 验证数据完整性
- TTL 过期数据不恢复
- AOF rewrite 后文件大小对比
- 向量数据恢复后 VINDEX REBUILD

#### 7. 边界
- AOF rewrite 不是后台子进程方式（和 Redis 不同）
- RDB 没有增量快照
- 没有 AOF-RDB 混合持久化

#### 8. 面试表达
> "做持久化最大的教训是：数据恢复不只是把数据读回来。TTL 要恢复、向量索引要重建、AOF 中的过期命令要正确处理。我花了很多时间在各种边界 case 的测试上——比如 AOF rewrite 过程中新写入的 TTL 怎么处理、RDB 加载后 AOF 重放会不会产生重复数据。"

### 第 5 篇：《主从复制：TCP 增量同步与 eBPF 辅助链路》

#### 1. 背景
- 单节点有 SPOF 风险
- 需要读写分离分担读压力

#### 2. TCP 主从同步
- 全量同步：RDB dump → 发送给 slave → slave 加载
- 增量复制：master 实时转发写命令
- 同步上下文管理（sync_context）：区分普通命令和复制命令

#### 3. eBPF 辅助同步
- 为什么：TCP 路径需要修改 master 代码转发命令，有 CPU 开销
- 原理：kprobe/tcp_sendmsg → ringbuf → ebpf_syncd → slave
- tx_batcher 批量优化

#### 4. 性能对比
- TCP 主从对写吞吐影响 <5%
- eBPF 路径批处理 vs 无批处理提升约 30%

#### 5. 边界（重点）
- 无断线续传（slave 断开后需要全量重新同步）
- 无故障自动切主
- eBPF 路径依赖内核版本和 BTF
- 从节点只读（不允许直接写入）

#### 6. 面试表达
> "主从复制最核心的概念是同步上下文——区分'用户命令'和'从主节点同步过来的命令'。从节点收到同步命令后设置 sync_context=2，执行命令但不再转发，防止无限循环。eBPF 路径是一个实验性的优化：通过内核探针直接抓取 TCP 报文，避免了主节点应用层的转发开销。"

### 第 8 篇：《向量语义检索：从 FLAT 到 HNSW》

#### 1. 背景

#### 2. 设计

- 插入算法：随机 level + 逐层搜索最近邻 + 建边 + 剪枝

#### 4. 验证

- 不支持增量删除（需 VINDEX REBUILD 回收空间）

- hash embedding 非语义模型
- 单线程搜索阻塞

#### 7.5 每节要点

**第 1 节：为什么写一个 KV 存储**
- 不要写"因为我对数据库感兴趣"这种空话
- 具体化：学完 CSAPP 的内存管理和网络编程后，想找一个"刚刚好"的项目验证所学
- Redis 代码量适中（核心约 2-3 万行），架构清晰，工业验证充分

**第 3 节：总体架构**
- 架构图必须画！用 mermaid 或者 draw.io
- 分层解释：网络层 → 协议解析 → 命令分发 → 存储引擎 → 持久化/复制
- 强调单线程执行模型：`pthread_rwlock` 保护全局数据结构，读命令拿读锁，写命令拿写锁

**第 4 节：演进路线**
- 这是整篇文章最核心的部分
- 用时间线 + 每个阶段的"做了什么 → 为什么做 → 收获了什么"格式
- 每个阶段引用 1-2 个代表性 commit hash
- 避免"我做了 A，又做了 B，又做了 C"的流水账

**第 7 节：已知局限**
- 这是整篇文章最重要的"可信度建设"
- 必须诚实、具体、不遮掩
- 每个局限写一句"为什么是局限"和"如果要做需要什么"

#### 7.6 必须画的图

1. **总体架构图**（必须） — 用 mermaid flowchart
2. **演进时间线图**（推荐） — 可以用 mermaid gantt 或手绘时间线
3. **请求处理流程图**（可选） — 展示从客户端到响应的完整路径

#### 7.7 应该出现的代码/伪代码

1. `command_info` 结构体的定义（展示命令表设计）
2. `kvs_filter_protocol` 的核心流程（伪代码）
3. `main` 函数的初始化流程（展示启动顺序）

**不要直接贴大段源码！** 用伪代码 + 关键结构体 + 文字解释。

#### 7.8 避免夸大的地方

| 不要写 | 应该写 |
|--------|--------|
| "高性能分布式 KV 数据库" | "类 Redis 的单机 KV 存储，支持基本主从复制" |
| "完全的 Redis 兼容" | "兼容 RESP 协议和基本 KV 命令" |
| "企业级持久化方案" | "实现了 AOF 和 RDB 两种持久化方式" |
| "生产级高可用" | "已实现基本主从同步，不支持自动故障切换" |
| "语义检索引擎" | "内置基于 hash embedding 的向量相似度搜索" |

#### 7.9 结尾引出下一篇

> "架构和演进路线给了我们全局视角。下一篇我们深入 RESP 协议解析和 Pipeline 批量处理——这是 KvLite 能用 redis-benchmark 压测、并在吞吐上追平 Redis 的技术基础。我们会看到，一个用户态缓冲区 + 批量解析的设计，如何将系统调用从 N 次降到 1 次。"

#### 7.10 如何反哺简历和面试

**简历项目描述（浓缩版）：**
> **KvLite — 类 Redis 内存 KV 存储系统**（C, ~37K 行, 个人项目）
