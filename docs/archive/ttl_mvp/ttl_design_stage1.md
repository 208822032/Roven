# KVLite TTL 改造分析 - 阶段1：方案设计

## 1. 设计结论

推荐方案：**存储层附加绝对过期时间 + 读时惰性删除 + 后台定期采样扫描的混合策略**。

核心判断：KVLite 目前的写入、持久化、复制都是命令驱动，且四类存储结构都以 key/value 为中心，没有现成的元数据层。因此，TTL 最适合以“key 的附属元数据”方式进入系统，而不是把过期逻辑分散到 AOF、RDB 或复制层各自独立维护。

建议的实现原则：

1. 过期信息与 key 生命周期绑定，删除 key 时必须同步删除过期元数据。
2. 读路径优先保证正确性，写路径优先保证简单性。
3. 持久化和复制只保存绝对过期时间，恢复后由当前时间重新判定是否过期。
4. 先做最小可行版本，再补齐增强版本，不一次性重构所有命令。

## 2. 方案对比

### 2.1 过期信息存储方式

#### 方案 A：嵌入 value 元数据

做法：把 expire 信息直接编码进 value，或者把 value 改成带过期字段的复合结构。

优点：

- 结构上看似最简单，不需要额外的索引容器。
- 单条 key 的读写都可以在一个对象内完成。

缺点：

- 会污染现有 value 语义。当前系统的 value 在很多路径里被当作纯字符串使用，包括 RESP 返回、AOF 重写、RDB 保存、复制消息、遍历输出。
- GET/SET/MOD/范围遍历都要去解包 value，侵入面大。
- 对 hash / rbtree / skiptable / array 四种结构而言，统一改造成本高，且容易破坏现有二进制兼容和字符串语义。

结论：**不推荐**。它适合做新系统，但不适合在当前仓库做低风险演进。

#### 方案 B：独立 expires 字典或索引

做法：保留现有 key/value 存储结构不变，另外维护一个过期索引，例如：

- key -> expire_at 的哈希表
- 或者按过期时间排序的辅助结构

优点：

- 对现有四类数据结构侵入较小，主数据结构基本不需要改成“带元数据对象”。
- 命令语义容易保持稳定，GET/DEL/EXIST 只需在进入底层之前先检查 TTL。
- RDB/AOF/复制扩展时，也更容易只新增 TTL 元数据，而不破坏原有 value 格式。

缺点：

- 需要维护两份状态，删除、覆盖、恢复时要保证一致性。
- 读路径和写路径都要做双查或同步更新。
- 如果只做独立字典而不做过期扫描，后台清理的成本会集中在读路径。

结论：**推荐，但不建议单独使用**，最好和后台扫描配合。

#### 方案 C：其他更适合当前项目的方式

做法：以“存储层节点附加 expire_at 字段”为主，必要时再配一个轻量过期索引。

判断：当前项目有四种结构，但都有统一的命令层和统一的持久化/复制层，因此最稳妥的方式是：

- 轻量修改存储节点或 item 结构，增加 expire_at 字段。
- 在需要高效过期清理时，再维护一个按过期时间组织的辅助结构。

结论：**推荐的最终方向是“节点内附加 expire_at + 可选辅助过期索引”**。如果要先做 MVP，也可以先只做节点内附加 expire_at，不加排序索引。

### 2.2 过期触发策略

#### 方案 A：惰性删除

做法：只在 GET / EXIST / RANGE / SORT / FULLDUMP 等读路径里检查是否过期，命中则删除并返回不存在。

优点：

- 实现最简单。
- 不需要后台线程。
- 对现有系统的写路径影响最小。

缺点：

- 冷 key 会一直占内存，直到被再次访问。
- 长尾过期 key 会积累，影响内存回收和遍历结果。
- 如果某些 key 很久不读，过期不会被主动清理。

结论：**适合做基础正确性层，但不适合作为唯一机制**。

#### 方案 B：定时扫描

做法：后台线程按固定周期扫描过期结构，主动删除到期 key。

优点：

- 能主动回收内存。
- 过期行为更接近用户预期。
- 对遍历类命令更友好。

缺点：

- 增加后台线程和同步复杂度。
- 如果扫描方式粗暴，会影响 QPS。
- 如果没有过期索引，定期全量扫描成本高。

结论：**适合作为增强层，但不建议单独作为唯一机制**。

#### 方案 C：混合策略

做法：

- 读路径做惰性删除，保证语义正确。
- 后台线程做定期扫描，负责主动清理。
- 如有需要，扫描优先看过期索引，避免全表扫。

优点：

- 正确性和资源回收都兼顾。
- 对现有 QPS 影响可控。
- 可以分阶段落地：先读时过期，再加后台清理。

结论：**推荐**。

### 2.3 时间表示

#### 秒级 vs 毫秒级

建议：**内部存储毫秒级，外部命令兼容秒级和毫秒级**。

理由：

- 秒级足够做基础 TTL，但与 Redis 类系统的预期相比颗粒度偏粗。
- 毫秒级更适合处理边界场景，尤其是复制、重启恢复、过期边界竞态。

#### 绝对时间戳 vs 相对 TTL

建议：**内部保存绝对过期时间戳 expire_at，命令层允许相对 TTL 输入**。

理由：

- 绝对时间戳更适合持久化和复制，因为它不依赖导入时刻。
- 相对 TTL 只适合交互式命令输入，恢复时还要再换算，容易引入偏差。

建议统一内部语义为：

- 命令输入：TTL / EXPIRE / PEXPIRE 使用相对时长。
- 持久化与复制：保存绝对 expire_at。

## 3. 命令层设计

### 3.1 是否新增命令

当前项目的命令体系是显式注册的，不是 Redis 那种动态命令扩展，因此建议分两步：

#### MVP 建议新增

- EXPIRE key seconds
- PEXPIRE key milliseconds
- TTL key
- PTTL key
- PERSIST key

#### 可选增强再加

- EXPIREAT key unix_seconds
- PEXPIREAT key unix_milliseconds
- SET key value EX seconds
- SET key value PX milliseconds

### 3.2 最小实现集

如果当前命令体系不适合完整兼容 Redis，最小实现集建议是：

1. EXPIRE
2. TTL
3. PERSIST
4. SET 覆盖时清 TTL 的规则

原因：

- 这四项就足以支撑“给 key 设置过期、读到过期、取消过期、覆盖时语义正确”。
- PEXPIRE / PTTL / EXPIREAT / PEXPIREAT 可以在 V2 补齐。

### 3.3 命令语义建议

- EXPIRE / PEXPIRE：为已有 key 设定过期时间。
- TTL / PTTL：返回剩余时间，key 不存在返回 -2，key 存在但无过期返回 -1。
- PERSIST：移除过期时间。
- SET 覆盖已有 key 时，默认清除原 TTL，除非显式带 EX / PX。

## 4. 覆盖语义

### 4.1 已有 TTL 的 key 再次 SET

建议：**默认清除 TTL**。

理由：

- 这符合常见 key-value 系统的直觉：SET 表示重建值，默认不继承旧生命周期。
- 实现上也最简单，减少隐式状态残留。

如果后续需要兼容 Redis 风格，可再加保留 TTL 的扩展选项，但不建议放进 MVP。

### 4.2 DEL 是否同步删除 expire 元数据

建议：**必须同步删除**。

理由：

- 避免悬挂元数据。
- 避免 key 被删除后过期索引还保留，导致重复清理或误判。

### 4.3 RENAME / 覆盖写 / 批量写

当前仓库未看到 RENAME 命令，因此只讨论已存在能力：

- 覆盖写：建议清 TTL，除非显式指定新 TTL。
- 批量写：如果未来新增批量写接口，每个 key 都必须单独处理 TTL，不要共享一个时间基准以外的隐式状态。
- FULLDUMP：如果未来要支持恢复级导出，必须把 expire_at 一并输出。

## 5. 性能影响

### 5.1 读路径增加的检查

新增的核心检查是：

1. 先查 key 是否存在。
2. 再查 expire_at 是否到期。
3. 如果到期，先删除再返回不存在。

对 GET / EXIST / RANGE / SORT 的影响：

- GET / EXIST：增加一次 TTL 检查和可能的一次删除。
- RANGE / SORT：在扫描过程中需要跳过过期 key，必要时顺带清理。
- FULLDUMP：导出前要过滤过期 key，否则恢复会带回已失效数据。

### 5.2 写路径增加的维护成本

新增成本主要有：

- SET / MOD / EXPIRE / PERSIST 需要同步维护过期元数据。
- DEL 需要双删。
- AOF / RDB / 复制需要额外序列化或反序列化 TTL。

### 5.3 对现有 QPS 的潜在影响

MVP 阶段的主要影响：

- 读路径增加一次过期判断，通常可控。
- 如果没有过期索引，后台扫描不做或做很轻，QPS 影响较小。

V2 阶段如果加过期索引：

- 读路径开销仍然很小。
- 写路径会增加维护索引的成本。
- 后台扫描要注意分批、限速、避免长时间持锁。

## 6. 推荐方案

### 推荐总方案

推荐采用以下组合：

- 内部存储绝对时间戳 expire_at，单位毫秒。
- 命令层支持 EXPIRE / PEXPIRE / TTL / PTTL / PERSIST，SET 覆盖默认清 TTL。
- 读路径做惰性删除。
- 后台做定时扫描，优先从过期索引中抽样清理。
- RDB、AOF、复制都传播绝对过期时间。

### 为什么适合当前仓库

1. 当前系统是显式命令表驱动，新增 TTL 命令很自然，改动边界清晰。
2. 当前四类存储都没有元数据层，TTL 如果嵌入 value 会破坏现有字符串语义；附加 expire_at 更符合仓库结构。
3. 当前 RDB/AOF/复制都以命令或 key/value 为载体，扩展绝对过期时间比扩展相对 TTL 更稳。
4. 复制链路已经是“命令转发 + slave 复执行”，非常适合把 TTL 作为附加参数传播。

## 7. 不推荐方案及原因

### 不推荐：把 TTL 直接塞进 value

- 会让所有数据结构和命令都感知 TTL，侵入面过大。
- 破坏当前“value 是纯字符串”的默认假设。

### 不推荐：只做惰性删除，不做后台扫描

- 冷 key 会长期占内存。
- 遍历命令和 FULLDUMP 容易持续带出已过期数据。

### 不推荐：只做后台扫描，不做读时检查

- 边界时刻语义不稳定。
- 如果扫描间隔较大，用户会看到过期延迟。

### 不推荐：只在 AOF 或 RDB 中保存 TTL

- 这会导致复制和内存状态不一致。
- 恢复后语义不完整，不能单独解决过期问题。

## 8. MVP 与 V2

### MVP

目标：先把 TTL 正确跑起来，避免大改现有系统。

建议范围：

1. 新增 expire_at 字段或独立过期表。
2. 增加 EXPIRE / TTL / PERSIST。
3. SET 覆盖清 TTL。
4. GET / EXIST / RANGE / SORT 做读时过期检查。
5. RDB 保存和加载 expire_at。
6. AOF 记录 TTL 命令或 SET EX 语义。
7. 主从复制同步 TTL 变更。

### V2

目标：把性能和语义补到更接近成熟 Redis 类系统。

建议范围：

1. 增加 PEXPIRE / PTTL / EXPIREAT / PEXPIREAT。
2. 增加后台过期扫描索引。
3. FULLDUMP 输出和恢复 TTL。
4. 批量写、未来新增重命名命令的 TTL 迁移语义。
5. 更细的过期统计和压测指标。

## 9. 风险与验证方式

### 风险

- 读写并发下 TTL 和底层数据删除要保证一致性。
- AOF 重放和复制重放可能与当前时间有关，必须统一使用绝对时间戳。
- FULLDUMP、RANGE、SORT 这类遍历接口很容易漏掉过期过滤。

### 验证方式

建议按阶段验证：

1. 单机功能测试：EXPIRE / TTL / PERSIST / 覆盖写 / 删除。
2. 恢复测试：RDB + AOF 重启后过期是否正确。
3. 复制测试：master/slave 上 TTL 是否一致。
4. 边界测试：过期前后同时读写、覆盖、删除、遍历。
5. 压测：比较无 TTL 与启用 TTL 时的 QPS 和延迟变化。

## 10. 本轮结论

KVLite 的 TTL 最适合走“附加元数据 + 混合过期策略”的渐进改造路线。它既能贴合当前命令驱动、命令回放、命令复制的结构，又不会把现有四类存储结构推翻重做。

建议下一阶段进入阶段 2：把方案拆成可落地的迭代计划，明确每一版要改哪些文件、先后顺序、验证点和回滚点。
